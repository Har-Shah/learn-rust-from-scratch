# Lesson 1.2 — Scalar types and integer overflow

**~35 minutes. Stopping point at the end.**

## What we're doing and why

You just saw `found usize` in an error message. This lesson explains what that is, why Rust has
twelve integer types where Python has one, and what happens when a number doesn't fit — which turns
out to depend on **how you built the program**.

That last part is the one to pay attention to. It is the first place where Rust makes a tradeoff you
would not have expected, and being unaware of it has caused real bugs in real software.

## Why twelve integer types

In Python, an integer is arbitrary precision. `2 ** 1000` just works; Python allocates more memory
as needed.

Rust integers are **fixed-width**. You pick how many bits, and that decision is permanent:

| | Signed | Unsigned |
|---|---|---|
| 8-bit | `i8` | `u8` |
| 16-bit | `i16` | `u16` |
| 32-bit | `i32` | `u32` |
| 64-bit | `i64` | `u64` |
| 128-bit | `i128` | `u128` |
| pointer-sized | `isize` | `usize` |

**The default is `i32`.** When you write `let x = 5;` with no annotation, that's what you get.

**`usize` is the one you'll meet constantly.** It's an unsigned integer the same width as a memory
address — 64 bits on your machine. It's the type Rust uses for *lengths and indices*, which is why
`.len()` returned it and broke your `&str`. A length can never be negative and can never exceed
what memory can address, and `usize` encodes both facts in the type.

**Why expose this at all?** Because Rust runs where Python doesn't: embedded chips, kernels, network
packets with exact byte layouts. When a protocol says a field is 16 unsigned bits, `u16` says so
exactly. There's also a real cost to Python's convenience — every Python integer is a heap-allocated
object with a reference count. A Rust `i32` is four bytes on the stack.

## What happens when a number doesn't fit

This is the part worth remembering.

```rust
let x: u8 = 255;   // u8 holds 0..=255, so this is the maximum
let y = x + 1;     // ???
```

Rust does **two different things** depending on how you built:

| Build | Behavior |
|-------|----------|
| **Debug** (`cargo run`) | **Panics.** The program crashes with "attempt to add with overflow". |
| **Release** (`cargo run --release`) | **Wraps.** `255 + 1` becomes `0`, silently. |

That is a deliberate and slightly uncomfortable tradeoff. Checking every arithmetic operation costs
performance, so release builds skip it. During development you get a loud crash; in production you
get silent wraparound.

**Don't file this as "Rust has a gotcha".** File it as: *if a value might overflow, say what you
want to happen.* Rust gives you explicit methods, and using them is the idiomatic answer:

```rust
let x: u8 = 255;

x.checked_add(1)      // Option — None on overflow, forces you to handle it
x.saturating_add(1)   // sticks at 255, the maximum
x.wrapping_add(1)     // wraps to 0, deliberately
x.overflowing_add(1)  // (0, true) — the value plus a did-it-overflow flag
```

Each states an intention. `x + 1` states none, which is why its behavior depends on a build flag.

## The other scalars, briefly

```rust
let a: f64 = 3.14;      // float — f64 is the default, f32 also exists
let b: bool = true;     // bool
let c: char = 'z';      // char — note SINGLE quotes
```

One surprise: a Rust `char` is **four bytes**, not one. It holds any Unicode scalar value — `'z'`,
`'é'`, `'🦀'` are all one `char`. This is not the same as a byte, and it is not the same as what
`String` stores internally either. That distinction gets its own lesson (1.6) because it causes
more confusion than anything else in Rust's standard library.

### 1. Trigger the panic

```rust
fn main() {
    let x: u8 = 255;
    let y = x + 1;
    println!("{y}");
}
```

```bash
cargo run
```

Read the panic message carefully. It names the file and line.

### 2. Now build for release

```bash
cargo run --release
```

Same source, different answer. Sit with that for a second.

### 3. Be explicit

Rewrite it using `checked_add(1)`. It returns an `Option` — you haven't formally met that type, so
just print it:

```rust
println!("{:?}", x.checked_add(1));
```

(`{:?}` is the *debug* format specifier. It prints things that don't have a nice display form.
You'll use it constantly.)

Run it in **both** debug and release. Compare to what `x + 1` did.

Your app will track a streak — consecutive days studied. What integer type would you choose, and
what should happen if it somehow overflows? Is this a `checked_`, `saturating_`, or `wrapping_`
situation? Justify it.
