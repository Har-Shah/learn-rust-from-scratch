# Lesson 1.1 — Bindings and mutability

**~35 minutes. Stopping point at the end.**

## What we're doing and why

You already met E0384 and fixed it by adding `mut`. That's the mechanical answer. This lesson is
the real question underneath it:

**Why did Rust make immutable the default, when Python, JavaScript, and Java all did the opposite?**

This is not a style preference. The answer is load-bearing for everything in Stage 2, and if it
lands now, ownership will make far more sense later.

## The mechanics first

```rust
let x = 5;        // immutable — this binding will never change
let mut y = 5;    // mutable — opting in
y = 6;            // fine
```

In Python, every name is rebindable and you say nothing about it. In Rust, you declare your
intent, and the compiler holds you to it.

## Why immutable by default

Three reasons, increasing in importance.

**1. Reading code becomes cheaper.**

In Python, seeing `total = 0` tells you nothing about what `total` is 40 lines later. Anything
could have touched it. You have to read all 40 lines to know.

In Rust, `let total = 0;` is a *guarantee*. Not a convention, not a naming style — the compiler
refuses to build the program if anything reassigns it. You can stop reading.

**2. `mut` becomes a signal.**

Because mutation is opt-in, every `mut` in a codebase is a small flag saying "this changes, pay
attention". If everything were mutable, that signal would carry no information.

**3. This is the foundation the borrow checker is built on.** ← the real reason

Here's the preview that matters. Almost every data-corruption bug — and *every* data race — needs
two things at once:

- more than one way to reach the data (**aliasing**)
- something changing it (**mutation**)

Either alone is harmless. Ten threads reading the same immutable value can't corrupt anything.
One thread mutating a value nobody else can see can't corrupt anything either. **The danger is the
combination.**

Rust's whole memory-safety story is built on separating those two. Making immutability the default
means the dangerous half is something you have to explicitly ask for — and once you've asked, the
compiler starts tracking who else can reach it.

That's Stage 2. But `mut` is not a syntax detail; it is the first half of the rule that makes Rust
memory-safe without a garbage collector.

## Shadowing — different from mutation

This compiles, with no `mut` anywhere:

```rust
let x = 5;
let x = x + 1;
let x = x * 2;
println!("{x}");   // 12
```

That is **not** mutation. Each `let` creates a *brand new binding* that happens to reuse the name.
The old one still exists — it is just no longer reachable by that name.

The distinction is visible when you change types:

```rust
let spaces = "   ";        // a string
let spaces = spaces.len(); // now a number — allowed
```

```rust
let mut spaces = "   ";
spaces = spaces.len();     // ERROR — a mutable binding keeps its type
```

**Shadowing makes a new variable, so the type may change. `mut` reuses one variable, so the type is
fixed.** You will produce that error yourself below.

Shadowing is idiomatic in Rust, and it is genuinely useful for the "parse this into its real type"
pattern you will write constantly:

```rust
let input = "42";                       // &str from the outside world
let input: u32 = input.parse().unwrap(); // now a number, same name
```

## `const` — a third thing

```rust
const MAX_USERS: u32 = 10_000;
```

Differs from `let` in ways worth knowing:

- The type annotation (`: u32`) is **required**, not optional
- Computed at compile time, so it cannot hold a value that must be worked out while running
- May be declared at any scope, including the top level of a file
- Always immutable — `const mut` does not exist
- Convention is `SCREAMING_SNAKE_CASE`

Use `const` for genuine constants. Use `let` for everything else.
